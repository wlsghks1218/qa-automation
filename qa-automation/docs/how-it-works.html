QA_Automation_KC 동작 흐름

URL 또는 기획서를 넣으면 테스트 케이스를 자동으로 만들고 실행해서 결과를 보여주는 프로그램 · v{{VERSION}} 기준

1. 한눈에 보기

STEP 1
입력
URL · 기획서(PDF 등) · 테스트 범위 · 브라우저 · 로그인 · 동작 확인 범위
로그인이 필요한 사이트
로그인 창에서 사람이 직접 로그인(ID/PW · SNS · 인증) → 로그인 상태를 저장해 이후 모든 단계에 사용
▼
STEP 2 · 크롤러
페이지 찾기
시작 페이지 → 세부 페이지 → 그 세부 페이지 … (같은 사이트만, 최대 50페이지)
다른 사이트 링크(광고 · 외부 링크)
페이지로 분석하지 않고, 누르면 그 사이트로 이동하는지만 확인
▼
STEP 3 · 하네스 generate-specs.js
페이지마다 화면 분석
버튼 · 링크 · 배너 · 입력창 · 검색창 · 드롭다운 · 표 · 문구 · 이미지 · 롤링 배너를 찾고, 실제로 눌러서 무슨 일이 일어나는지 관찰
기획서를 넣은 경우
AI가 기획서로 TC를 쓰고, 그 TC를 STEP 3에서 찾은 화면 요소와 연결
▼
STEP 4
테스트 케이스 생성
화면 위→아래 순서로 요소마다 노출 · 문구 · 동작 확인 항목을 만들고, 규칙 기반 오타 의심 검사 · cases.html(실행 전) 저장
AI 테스트 버튼
페이지 화면 캡처 + 요소 목록을 AI에게 보내 기대 동작 TC와 화면 이슈(오타 · 레이아웃 등)를 추가
▼
STEP 5 · Playwright
실행 = 실제 사이트와 비교
Chrome · Safari(WebKit) · Firefox에서 새 브라우저로 사이트를 다시 열고, 분석 때 관찰한 결과대로 동작하는지 하나씩 확인 (진행률 표시 · 중지 가능)
비교 기준
① 분석 때 실제로 관찰한 동작
② 기획서에 적힌 기대 결과
③ AI가 판단한 기대 동작
▼
STEP 6
결과
앱 화면 결과 · cases.html(대분류 · 중분류 · 소분류 · 과정 · 기대결과 · 결과 · 이유) · Playwright 리포트(실패 스크린샷 · 영상) · run.log
결과 폴더에 실행마다 따로 저장
CSV(엑셀)로도 내려받기 가능
핵심 원리: 이 프로그램은 사람이 하듯 화면을 직접 눌러 보고(분석), 그때 본 결과를 테스트 코드로 고정한 뒤(생성), 새 브라우저에서 다시 해 봐서 같은 결과가 나오는지 확인합니다(실행). 기획서나 AI를 쓰면 "관찰한 결과" 대신 "기대해야 하는 결과"와 비교할 수 있습니다.

2. STEP 1 · 입력

항목내용
URL테스트할 사이트 주소. 기획서만 넣으면 TC 작성까지만 진행
기획서 첨부PDF · 이미지 · 문서. AI API Key(Gemini · Claude · ChatGPT 중 선택)가 필요
테스트 범위세부 사이트 모두: 연결된 세부 페이지까지 / 입력한 페이지만: 그 페이지 하나
브라우저Chrome · Safari(WebKit 엔진) · Firefox. 여러 개 고르면 브라우저마다 실행하고 결과 차이를 따로 표시
로그인URL을 넣으면 로그인 화면인지 자동 확인 → 로그인 창 열기에서 직접 로그인 → 로그인 완료. 사이트별로 이 PC에만 저장
동작 확인 범위안전(기본): 삭제 · 결제 · 제출 · 저장 · 출근처럼 데이터가 바뀌는 버튼은 누르지 않고 노출 · 문구만 확인
전체 동작 확인: 그런 버튼도 실제로 누름 (테스트 계정 · 테스트 서버 전용). 탈퇴 · 결제 · 송금 · 로그아웃은 항상 누르지 않음
실행 버튼규칙 기반 테스트(AI 없이) / AI 테스트(규칙 기반 + AI 화면 분석)

3. STEP 2 · 페이지 찾기 (크롤러)

시작 페이지→링크 수집→1단계 세부 페이지→2단계 …→새 페이지 없음 / 50개 도달
규칙설명
같은 사이트서브도메인 포함 (www.naver.com · news.naver.com 은 같은 사이트). 단, lovable.app · vercel.app 같은 호스팅 도메인은 서브도메인마다 다른 사이트
다른 사이트광고 배너 · 외부 링크는 분석하지 않고 "누르면 그 사이트로 이동하는지"만 테스트
중복 제거/notice/1, /notice/2처럼 ID만 다른 상세 페이지는 하나만 · 광고 추적값(utm_…)만 다른 주소는 같은 페이지
파일 링크PDF · 이미지 · 압축 파일은 페이지로 분석하지 않음
접속 차단봇 차단 · 보안 확인 화면이면 "접속 차단"으로 표시하고 접속 상태만 검사

4. STEP 3 · 페이지 분석 (하네스 generate-specs.js)

페이지마다 새 브라우저로 열고, 화면 구조(DOM · 위치 · 스타일)를 읽어 테스트할 대상을 찾은 뒤, 요소를 실제로 눌러서 결과를 관찰합니다. 특정 사이트에 맞춘 규칙 없이 화면 구조만으로 판단합니다.

3-1. 무엇을 찾는가

대상찾는 방법만들어지는 확인 항목
버튼 · 링크 · 탭클릭 가능한 모든 요소노출 · 문구 · 동작
배너 · 로고넓은 영역에 여러 줄 문구/이미지를 담은 클릭 요소 · 헤더 왼쪽 위 이미지노출 · 문구(줄마다) · 이미지 로드 · 동작
일반 문구 · 이미지클릭 요소 밖의 텍스트 덩어리 · 대체텍스트가 있는 이미지노출 (숫자는 형식만)
롤링 배너몇 초간 9번 관찰해 보였다 사라지는 문구를 같은 영역끼리 묶음 (좌우 · 상하 · 페이드)문구가 차례로 화면에 나타남
툴팁마우스를 올렸을 때 요소 근처에 새로 나타나는 문구마우스 오버 노출
입력창 · 검색창입력 요소 · 이름에 "검색/조회/필터"가 있으면 검색창입력 · 목록의 실제 값으로 검색 → 그 값만 표시 · 없는 값 → 결과 없음
드롭다운선택 박스(select) · 누르면 옵션(option/menuitem)이 나타나는 버튼옵션을 하나씩 선택(최대 8개) → 선택 값 표시 / 목록 변경 / 페이지 이동
표머리글이 있는 표열 구성 · 모든 행의 칸 수 · 열별 형식(날짜 · 시간 · 숫자) · 정렬 버튼
반복 목록같은 목록 안 같은 위치 · 같은 종류 요소 3개 이상 (표의 행 버튼 · 달력 날짜 · 상세 링크)대표 1개만 테스트 ("목록 N개 중 대표") · 상세 링크면 목록 → 상세 → 뒤로가기 흐름
입력 검증입력창의 필수(required) · 형식(email · url · pattern) · 최대 길이(maxlength)빈 값 · 잘못된 형식 · 긴 값이 거부되는지 (제출하지 않고 브라우저 검증으로 확인)
호버 메뉴마우스를 올렸을 때만 나타나는 하위 링크 (메가 메뉴)올리면 나타나고, 누르면 해당 페이지로 이동
임베드 · 웹 컴포넌트iframe(지도 · 결제 · 영상) · Shadow DOM 안의 버튼 · 문구iframe 정상 로드 · Shadow DOM 요소는 일반 요소와 같게 테스트

3-2. 눌러서 관찰하는 결과 (동작 유형)

관찰 결과판단 기준테스트에서 확인하는 것
페이지 이동주소가 바뀜같은 주소로 이동 (외부 사이트는 도메인만)
새 탭 열기팝업 창이 열림새 탭이 열리고 해당 사이트로 감
모달 · 시트화면 위에 고정된 새 층이 나타남열림 → 닫기 버튼/ESC로 닫힘 (문구 개수가 늘었다 원래대로)
펼침 · 접힘aria-expanded 변화펼쳐졌다가 다시 누르면 접힘
탭 전환aria-selected 변화해당 탭이 선택됨
표 정렬표 머리글 버튼 클릭 후 행 순서 변화행 순서가 바뀜
콘텐츠 노출화면에서 찾을 수 있는 새 문구가 나타남 (숫자만 바뀐 줄은 제외)그 문구가 나타남
깨진 링크브라우저 오류 페이지로 감정상 페이지로 열리는지 (현재 상태면 실패로 보고)
파일 다운로드다운로드가 시작됨 (엑셀 다운로드 등)파일이 내려받아지고 비어 있지 않음
목록 페이지 이동다음 · 이전 · 페이지 번호를 누르면 목록 내용이 바뀜누르면 목록이 바뀜
클릭 안정성눈에 보이는 변화 없음눌러도 JS 오류가 없음

3-3. 페이지 단위 점검 (페이지마다 자동 추가)

케이스확인 내용판정
00. 페이지 로드HTTP 응답 · 깨진 이미지 · JS 오류 · 같은 사이트 요청 실패(404 · 5xx · 연결 실패) · iframe 로드실패
00. (경고 항목)console.error · https 페이지의 http 리소스 · 성능(LCP 4초 · 전체 로드 10초 초과)경고
00-1. 모바일 화면390×844 화면에서 화면보다 넓은 요소(가로 스크롤)실패
00-2. 접근성axe-core 로 WCAG 2 A/AA 검사 (이미지 대체텍스트 · 라벨 · 대비 · 제목 순서 등)경고
00-3. 404 처리시작 페이지에서만: 없는 주소를 열면 404 상태나 "찾을 수 없음" 안내가 나오는지경고
00-4. 공통 메뉴 노출세부 페이지마다 시작 페이지의 헤더 · 메뉴 · 푸터가 보이는지실패

3-4. 오판을 막는 장치

상태 격리

페이지마다 새 브라우저로 분석하고, 클릭할 때마다 쿠키 · 저장소를 처음 상태로 되돌림. 예) 다른 페이지에서 접은 사이드바가 다음 분석에 섞이지 않음

바뀌는 값 처리

숫자가 든 문구(건수 · 날짜 · 시간)는 형식만 비교 · 알림 배지 숫자는 무시 · 시계/카운트다운 · 롤링 문구는 클릭 결과로 보지 않음

안전 모드

삭제 · 결제 · 제출 · 저장 · 출근 · 로그아웃 등은 누르지 않고 노출 · 문구만 확인. 팝업은 "확인" 대신 닫기 · 취소 · ESC로 닫음

찾기 쉬운 로케이터

Playwright 권장 순서: 역할+이름 → 라벨 → placeholder → 링크 주소 → 고유 속성 → 태그+문구. 이름 끝 숫자 배지는 "있어도 없어도" 찾음

5. STEP 4 · 테스트 케이스 생성

분석 결과 (analysis.json)→화면 위→아래 정렬→요소마다 확인 항목→Playwright 코드 (*.spec.ts)+cases.html (실행 전)

한 요소 = 한 케이스, 케이스 안에서 확인 항목을 각각 따로 판정합니다. 예) 배너 "USDT 결제, QR 하나면 끝!"

확인 항목내용
노출화면에 보이는가 (실패하면 나머지 항목은 "확인 불가"로 건너뜀)
문구요소 안 문구를 줄마다 확인 (숫자는 형식만)
이미지 로드요소 안 이미지가 깨지지 않았는가
마우스 오버툴팁 문구가 나타나는가
동작3-2의 관찰 결과대로 동작하는가
대체 로케이터기본 이름으로 못 찾으면 화면 문구 → 구조 경로 순으로 다시 찾음. 찾으면 테스트는 계속하고 "이름이 바뀌었을 수 있음" 경고
오타 의심실패가 아닌 경고. 사이트 전체 문구 비교(자주 쓰인 단어와 헷갈리는 자모 하나 차이) · 형식 오류(단어 반복 · 괄호 짝 · 낱자모) · 자주 틀리는 표기(되요 · 몇일 · 할께 …)

분석이 끝나면 결과 폴더에 cases.json과 cases.html(모든 항목 "미실행")이 먼저 저장됩니다.

6. STEP 5 · 실행 (사이트와 비교)

새 브라우저→(저장된 로그인 적용)→페이지 열기 · 팝업 처리→확인 항목 순서대로 실행→항목별 통과/실패 기록
설정값이유
동시 실행4개사이트에 요청이 몰리면 무더기 타임아웃 · PC 메모리 보호
재시도1회일시적 네트워크 지연. 재시도로 통과하면 "불안정"으로 표시
화면 · 언어분석 때와 동일1440×900, 분석한 PC의 언어 · 시간대로 고정해 문구가 달라지지 않게
진행률앱 화면 프로그레스 바분석: 페이지 수 · 실행: 끝난 케이스 / 전체 (통과 초록 · 실패 빨강)
중지중지 버튼실행 중인 분석 · 테스트와 브라우저를 즉시 종료
"사이트와 비교"의 의미 — 규칙 기반 테스트의 기대 결과는 분석 때 실제로 관찰한 동작입니다. 그래서 "지금 사이트가 분석 시점과 같은 화면 · 같은 동작인가"를 확인하는 회귀 테스트에 강합니다. "원래 이렇게 동작해야 한다"를 확인하려면 기획서(기획서의 기대 결과와 비교)나 AI 테스트를 함께 씁니다.

7. STEP 6 · 결과

실행마다 결과 폴더(기본: 문서/QA_Automation_KC, 앱에서 변경 가능) 아래 날짜-시간 폴더가 만들어집니다.

8. 선택 기능

기획서 URL + 기획서

  • AI가 기획서를 읽고 TC 작성
  • TC마다 STEP 3에서 찾은 화면 요소와 연결
  • 연결된 TC는 기획서의 기대 결과로 실행 · 못 찾은 TC는 "화면에서 못 찾음" · 판단 불가는 "수동 확인 필요"
  • 기획서와 실제 동작이 다르면 "실제 동작 차이"로 표시

AI 테스트 URL만

  • 페이지 화면 캡처 + 요소 목록을 AI에 전송
  • AI가 기대 동작 기준 TC를 작성해 함께 실행
  • 이미지 속 글자 · 맞춤법 · 어색한 문구 · 레이아웃 이슈 보고

보안 로그인 정보 보호

  • 저장된 로그인은 Windows 계정 암호화(DPAPI)로 저장, 실행 중에만 임시로 풀고 끝나면 삭제
  • 기본 7일이 지나면 자동 삭제 (settings.json 의 authMaxAgeDays)
  • 로그인으로 실행하면 트레이스(쿠키 포함)를 남기지 않음 · 결과에 "외부 공유 주의" 표시
  • 운영 사이트로 보이면 로그인 전 경고 · AI 테스트는 로그인 화면 전송 동의를 한 번 받음

로그인 로그인이 필요한 사이트

  • 로그인 화면 자동 감지
  • 사람이 직접 로그인 (어떤 방식이든)
  • 저장된 로그인으로 분석 · 실행, 만료 시 다시 로그인 안내

전체 동작 확인 테스트 계정 전용

  • 저장 · 등록 · 제출 · 삭제 버튼도 실제로 눌러 확인
  • 분석 · 브라우저별 실행 · 재시도마다 반복해서 눌릴 수 있음

9. 알아둘 한계

  • 이미지 안에 그려진 글자 · canvas 화면은 규칙 기반으로 읽지 못함 (AI 테스트로 보완)
  • 숫자가 든 문구는 형식만 비교하므로 "10% → 7%" 같은 값 변경은 규칙 기반으로 잡지 못함 (기획서로 보완)
  • 규칙 기반의 기대 결과는 "분석 시점의 동작"이라, 분석 시점에 이미 잘못된 동작은 정상으로 기록됨
  • iframe 은 정상 로드만 확인하고, iframe 안의 버튼 · 문구는 하나씩 테스트하지 않음
  • 입력 검증은 브라우저 기본 검증(required · type · pattern · maxlength)만 확인. 스크립트로 직접 만든 검증 메시지는 제출해야 보여서 확인하지 않음
  • 승인된 기준이 없으면 변경 감지는 직전 실행과 비교하므로, 기준을 승인하기 전에는 이미 있던 문제가 변경으로 드러나지 않음
  • 화면 구조가 이전 분석과 같으면 클릭 탐지를 다시 하지 않고 이전 분석을 재사용 (동작만 바뀐 경우는 테스트 실행에서 실패로 드러남)
  • 서버에 저장되는 설정(계정 설정 등)은 분석 후 되돌릴 수 없음 (전체 동작 확인을 켰을 때만 해당)

10. 결과를 믿을 수 있게 하는 장치

10-1. 승인된 기준선

규칙 기반 테스트의 기대 결과는 "분석할 때 관찰한 동작"이라, 분석 시점에 이미 잘못된 동작은 정상으로 기록됩니다. 그래서 사람이 한 번 검토하고 승인한 결과를 기준으로 고정합니다.

단계내용
승인결과 화면에서 실패 · 변경 · 커버리지를 검토한 뒤 이 결과를 기준으로 승인. URL · 범위별로 분석 결과 · 테스트 코드 · 화면 캡처를 저장하고 승인 시각 · 승인자(Windows 사용자) · 앱 버전을 기록. 이전 기준은 이력으로 보관
기준 대비 변경새로 분석하면 직전 실행이 아니라 승인된 기준과 비교해 달라진 점을 표시. 한 번 들어간 버그가 다음 실행부터 정상으로 굳지 않음
기준으로 테스트"승인된 기준으로 테스트"를 켜면 분석 없이 기준의 테스트를 그대로 실행 (기대 결과 = 승인한 동작). 빠르고 결과가 기준에 고정됨
기준 갱신사이트가 의도적으로 바뀌었으면 새로 분석한 결과를 검토하고 다시 승인. 해제하면 직전 실행 비교로 돌아감

10-2. 하네스 자가 검증

하네스(분석 · 테스트 생성 규칙)를 고칠 때 기존 감지가 깨지지 않았는지, 정상 화면을 실패로 판정하지 않는지를 버그를 일부러 심은 테스트 사이트로 확인합니다 (npm run selftest, 릴리스 전 실행).

  1. 테스트 사이트(정상 모드)를 분석해 테스트 생성
  2. 정상 모드에서 실행 → 실패가 하나라도 있으면 오탐
  3. 버그 16개를 넣은 모드에서 같은 테스트 실행 → 버그마다 해당 케이스가 실패하면 감지
