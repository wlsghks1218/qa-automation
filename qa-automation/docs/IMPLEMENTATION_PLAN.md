# QA_Automation_KC 입력 확장 구현 계획

QA 대행 의뢰서 수준의 입력(URL · 기획서 · 계정 · 실행 환경 · Figma · API 문서 · Jira)을 받을 수 있도록 확장한다.
**한 번에 Phase 하나씩** 구현하고, Phase 하나 = 버전 하나(0.001 증가)로 배포한다.

---

## 공통 규칙 (모든 Phase에 적용)

1. **기존 동작 유지:** 새 입력은 모두 선택 사항이다. URL만 넣고 실행하는 기존 흐름(규칙 기반 · AI 테스트 · 기획서 모드)은 그대로 동작해야 한다.
2. **비밀값은 전부 암호화:** 비밀번호 · API 토큰(Figma · Jira · API 인증) · Basic 인증 정보는 `app/secure-store.js`(Electron `safeStorage`)로만 저장한다. `settings.json`, `.env`, 결과 폴더, 리포트, `run.log`, `cases.html`에는 **절대 평문으로 남기지 않는다.** 로그에는 `****`로 가린다.
3. **안전 모드 존중:** 새 기능도 안전 모드(기본)에서는 데이터를 바꾸는 동작(POST · PUT · DELETE 호출, 저장 · 제출 버튼, Jira 등록)을 하지 않는다. 외부로 쓰는 동작(Jira 등록 등)은 **항상 사람이 확인한 뒤에만** 실행한다.
4. **실패해도 전체는 계속:** Figma · Jira · API 문서를 읽지 못해도 분석 · 실행은 계속하고, 결과에 "○○ 연동 실패: 이유"로 남긴다.
5. **버전 · 문서:** Phase마다 `npm run version:bump`, `docs/changelog.json`에 변경 내용 추가, `docs/how-it-works.html` 갱신 후 `npm run doc`.
6. **UI 문구는 한국어,** 기존 화면 스타일(`app/public/index.html`)을 따른다.

## Phase 0. 공통 기반: 입력 모델과 비밀값 보관

**목표:** 이후 Phase들이 쓸 "실행 설정" 구조와 비밀값 저장소를 만든다.

- **실행 설정 객체(`runConfig`)** 를 정의하고 `/api/run` 요청 body를 이 구조로 받는다. 기존 필드(`url`, `scope`, `mode`, `browsers`, `file`, `useLogin`, `clickAll`)는 그대로 받아 변환한다(하위 호환).
  ```js
  runConfig = {
    target:   { url, envType: 'beta' | 'staging' | 'production' },
    runtime:  { browsers: ['chromium','webkit','firefox'], viewports: ['desktop','mobile'] },
    scope:    { mode: 'all' | 'single' | 'pages' | 'changes', pages: [], exclude: { urlPatterns: [], buttonTexts: [] } },
    access:   { basicAuth: secretRef | null, headers: secretRef | null },
    accounts: [ { role: '일반회원', method: 'manual' | 'credentials', secretRef } ],
    spec:     { file, link },
    figma:    { fileUrl, secretRef } | null,
    api:      { specUrlOrFile, baseUrl, auth: secretRef } | null,
    jira:     { siteUrl, projectKey, epicKeys: [], secretRef, createBugs: false } | null,
    testData: { freeText, knownIssues: [] },
    safety:   { clickAll },
  }
  ```
- **`app/secure-store.js` 확장:** `saveSecret(id, value)`, `readSecret(id)`, `deleteSecret(id)`, `listSecrets()`를 추가한다. 저장 위치는 `USER_DIR/secrets/<id>.enc`. 화면과 `runConfig`에는 값이 아니라 `secretRef`(id)만 주고받는다.
- **"프로젝트" 저장:** 사이트별로 마지막 `runConfig`(비밀값 제외)를 `USER_DIR/projects/<host>.json`에 저장해, 다음 실행 때 자동으로 채운다.
- **화면 재구성:** 입력 영역을 **[필수] / [권장] / [선택]** 세 묶음으로 나눈다. [선택]은 접힌 상태가 기본이다.

**완료 기준:** 기존처럼 URL만으로 실행해도 결과가 같다. 비밀값을 저장 · 읽기 · 삭제할 수 있고, 결과 폴더 전체를 검색해도 비밀값 평문이 나오지 않는다.

## Phase 1. 대상 · 실행 환경 · 범위 · 접속 조건

**목표:** 실무 의뢰서의 기본 항목을 받는다.

1. **환경 종류:** 베타 / 스테이징 / 운영 선택.
   - **운영**이면 "전체 동작 확인"을 끄고 비활성화하며, 경고를 표시한다("운영 서버: 데이터가 바뀌는 동작은 하지 않습니다").
   - 선택하지 않으면 host로 추정한다(`dev`, `stg`, `staging`, `test`, `qa`, `beta`, `localhost`이면 테스트 환경, 아니면 운영으로 가정).
2. **실행 환경과 테스트 범위 분리:**
   - 실행 환경: 브라우저(기존) + **화면 크기 PC(1440×900) / 모바일(390×844, 터치)**. 모바일을 고르면 분석과 실행을 모바일 화면으로도 수행한다(`devices['iPhone 15']` 등 Playwright 기기 프리셋).
   - 테스트 범위: 전체 사이트 / 입력한 페이지만 / **지정한 페이지 목록** / **변경분**(Phase 4 Jira 또는 직전 실행 대비 변경 페이지).
3. **접속 조건:** Basic 인증(아이디 · 비밀번호) → Playwright `httpCredentials`. 추가 HTTP 헤더(예: 우회 토큰) → `extraHTTPHeaders`. 모두 비밀값으로 저장한다. 분석(`generate-specs.js`), 로그인 창, 실행(`playwright.generated.config.js`)에 모두 적용한다.
4. **제외 영역:** URL 패턴(예: `/admin/*`)은 크롤링하지 않는다. 버튼 문구(예: "주문하기")는 누르지 않는 목록에 추가한다(기존 안전 모드 목록에 합치기).
5. **테스트 데이터 · 알려진 이슈(자유 입력):**
   - 테스트 데이터(검색어, 쿠폰 코드 등)는 검색창 · 입력창 테스트 값으로 우선 사용한다.
   - 알려진 이슈와 같은 실패는 결과에 "알려진 이슈"로 표시하고, 실패 수에서 따로 센다.

**완료 기준:** Basic 인증이 걸린 사이트를 분석 · 실행할 수 있다. 운영 환경에서는 전체 동작 확인을 켤 수 없다. 모바일을 고르면 모바일 결과가 PC 결과와 따로 표시된다. 제외한 URL과 버튼은 분석에 나타나지 않는다.

## Phase 2. 권한별 테스트 계정

**목표:** 일반회원 · 관리자처럼 여러 계정으로 테스트한다.

- 계정 목록 UI: `역할 이름` + 방식(**직접 로그인** / **계정 전달**).
  - **직접 로그인:** 기존 `login-session.js` 흐름을 그대로 쓴다. 저장 파일만 역할별로 나눈다(`auth/<host>__<role>.json.enc`).
  - **계정 전달:** 아이디 · 비밀번호를 비밀값으로 저장한다. 실행 전에 로그인 화면에서 자동으로 로그인을 시도한다(아이디 · 비밀번호 입력창을 라벨 · 타입으로 찾기). 실패하면(MFA · 캡차 등) "직접 로그인 필요"로 안내하고 직접 로그인으로 전환한다.
- 입력 화면에 **"테스트 계정만 입력하세요. 개인 · 관리자 실계정은 입력하지 마세요"** 안내를 고정 표시하고, MFA 해제 여부 체크박스를 둔다.
- 실행: 계정마다 분석 · 실행을 반복한다. 결과의 대분류 앞에 `[역할]`을 붙인다(예: `[관리자] /dashboard`). 역할에 따라 보이는 메뉴 차이도 결과에 표시한다.
- 로그인하지 않은 상태(비회원)도 기본으로 하나의 "역할"로 실행한다(선택 해제 가능).

**완료 기준:** 계정 두 개(예: 일반 · 관리자)로 실행하면 역할별 결과가 나뉘어 나온다. 비밀번호는 암호화 파일에만 있다.

## Phase 3. 기획서 링크

**목표:** 파일 첨부 외에 링크로도 기획서를 받는다.

- 공개 URL(웹 페이지 · PDF 링크): 내려받아 기존 기획서 처리(`app/doc-testcases.js`)로 넘긴다. PDF는 파일로, HTML은 본문 텍스트로 넘긴다.
- 로그인이 필요한 문서(Google Docs · Confluence · Notion): 이번 Phase에서는 **"공개 링크나 PDF로 내보내서 첨부해 주세요"** 안내만 한다(연동은 나중에).
- 첨부와 링크를 동시에 주면 둘 다 기획서로 합쳐서 쓴다.

**완료 기준:** 공개 PDF 링크만 넣어도 기획서 모드가 동작한다.

## Phase 4. Jira 연동 (입력 + 버그 등록)

**목표:** Jira 에픽을 요구사항과 변경 범위로 쓰고, 실패한 테스트를 Jira 버그로 등록한다.

- **연결:** Jira 사이트 URL(`https://xxx.atlassian.net`) + 이메일 + API 토큰(비밀값) + 프로젝트 키. "연결 확인" 버튼으로 `/rest/api/3/myself`를 호출해 확인한다.
- **입력(읽기):**
  - 에픽 키(여러 개)를 입력하면 하위 이슈의 제목 · 설명 · 인수 조건을 읽는다.
  - 이것을 기획서처럼 AI로 TC로 만들어 화면 요소와 연결한다(`doc-testcases.js` 재사용). TC에는 출처 이슈 키를 남긴다.
  - 범위가 "변경분"이면 이슈에 나온 화면 · 기능 위주로 테스트한다.
- **출력(버그 등록):** 기본은 꺼짐이다.
  - 실행이 끝나면 실패 케이스마다 **버그 초안**을 만든다. 제목, 재현 절차(과정), 기대결과, 실제결과, 브라우저 · 화면, 스크린샷을 담는다.
  - 결과 화면에서 사람이 체크한 것만 **"Jira에 등록"** 버튼으로 등록한다. 스크린샷은 첨부하고, 관련 에픽이나 이슈가 있으면 링크한다.
  - **중복 방지:** 같은 케이스 ID로 이미 열린 버그가 있으면 새로 만들지 않고 "이미 등록됨(키)"으로 표시한다. 라벨 `qa-kc`와 케이스 ID를 이슈에 남겨 검색한다.
  - 저장된 로그인으로 실행한 결과의 스크린샷은 등록 전에 **"로그인 화면이 포함됩니다"** 경고를 띄운다.
- **결과:** `cases.html` "이유" 열 옆에 Jira 키 링크를 표시한다.

**완료 기준:** 에픽 키로 TC가 생성되어 실행된다. 체크한 실패 케이스만 Jira 버그로 한 번씩 등록되고, 다시 실행해도 중복 등록되지 않는다.

## Phase 5. API 문서 → API 테스트

**목표:** OpenAPI(Swagger) 문서로 API 테스트를 만들어 실행한다.

- **입력:** OpenAPI JSON/YAML 파일 또는 URL, API base URL, 인증(Bearer 토큰 · API 키 헤더 · 저장된 로그인 쿠키 재사용 중 선택, 비밀값).
- **생성:** 엔드포인트마다 Playwright `request` 테스트를 만든다(`tests/generated/api/*.spec.ts`).
  - 상태 코드가 문서의 응답 코드와 같은지
  - 응답 본문이 문서의 스키마와 맞는지(필수 필드 · 타입). 스키마 검사는 `ajv` 같은 라이브러리를 쓴다.
  - 응답 시간(경고 기준, 예: 2초)
  - 인증이 필요한 API를 인증 없이 부르면 401 또는 403인지
- **안전:** 안전 모드에서는 **GET만** 실행하고, POST · PUT · PATCH · DELETE는 "건너뜀(안전 모드)"으로 둔다. 전체 동작 확인 + 운영이 아닌 환경일 때만 쓰기 API를 실행한다. 경로 파라미터 값은 GET 목록 응답이나 테스트 데이터에서 가져온다.
- **기획서 연결:** 기획서가 있으면 AI가 TC와 관련 API를 짝지어, 화면 TC 실패 시 관련 API 결과를 같이 보여 준다.
- **결과:** `cases.html`에 대분류 "API"로 표시한다(중분류 = 엔드포인트, 소분류 = 확인 항목).

**완료 기준:** 공개 예제 OpenAPI(예: Swagger Petstore)로 GET 테스트가 생성 · 실행된다. 안전 모드에서 쓰기 API는 호출되지 않는다.

## Phase 6. Figma 시안 비교

**목표:** 실제 화면이 디자인 시안과 다른 곳을 찾는다.

- **입력:** Figma 파일 링크 + 개인 접근 토큰(비밀값).
- **처리:**
  1. Figma REST API(`/v1/files/:key`, `/v1/images/:key`)로 프레임 목록과 이미지를 가져온다.
  2. **프레임 ↔ 페이지 연결:** AI가 프레임 이름 · 문구와 분석한 페이지를 짝짓는다. 사람이 화면에서 확인하고 수정할 수 있게 한다. 연결 결과는 프로젝트에 저장한다.
  3. 연결된 페이지마다 같은 화면 크기로 스크린샷을 찍어 시안과 비교한다.
     - **문구 비교(확정 검사):** Figma 텍스트 노드와 화면 문구를 비교해 다른 문구를 실패로 표시한다.
     - **화면 비교(경고):** 시안 이미지와 스크린샷을 AI에 보내 레이아웃 · 색 · 누락 요소 차이를 경고로 보고한다. 픽셀 비교는 오탐이 많으므로 쓰지 않는다.
- **결과:** `cases.html`에 대분류 "디자인 비교", 시안과 실제 화면을 나란히 보여 주는 링크.

**완료 기준:** 연결된 페이지마다 문구 차이가 실패로, 레이아웃 차이가 경고로 나온다. 토큰이 없거나 틀리면 이 단계만 건너뛴다.

## Phase 7 (나중). 모바일 앱

- 입력이 URL이 아니라 **APK(Android) / IPA 또는 시뮬레이터 빌드(iOS)** 이다. Appium(또는 Maestro) 기반의 별도 실행기가 필요하다.
- 웹과 같은 흐름(화면 요소 찾기 → 눌러 보기 → 테스트 생성 → 실행)을 앱 접근성 트리로 구현한다.
- 웹 기능이 안정된 뒤 별도 계획으로 진행한다.
